# ERA-002: Request a fresh proposal from one independent adapter

Epic: [EPIC-01](../epics/EPIC-01.md). Milestone: v0.1 end-to-end demonstration. Status: proposed.

Delivery and acceptance owner: project owner. Source-behavior decisions also require the accountable source owner.

## Outcome

An operator records a customer request and receives a fresh cleanup proposal for a seeded source.

## Requirements and dependencies

Requirements: REQ-04, REQ-05.

Depends on: [ERA-001](ERA-001.md).

## Intended implementation ownership

- `backend/cases/`
- `backend/proposals-decisions/`
- `contracts/`
- `adapters/transactional/`
- `frontend/requests/`

## Acceptance criteria

- [ ] Record external request reference, tenant, UTC half-open interval, and a registered-source snapshot.
- [ ] Run the adapter separately and let it poll a source-scoped proposal command; it alone reads its source store.
- [ ] Return an immutable plan with selection token, affected counts, action, expiry, and source/mapping/policy versions.
- [ ] Show proposal details in the request view; do not use an inventory estimate as execution authority.

## Verification

Exercise operator → command → adapter → proposal → UI on fixture records at both interval boundaries; unauthorized adapter publication fails.

Retain commands/results and owner review against the exact candidate. Application checks are implemented with the issue; these are acceptance instructions, not claims that tests already exist.

Use the [product requirements](../../docs/specification.md) and [architecture contract](../../docs/architecture.md). Operate on synthetic data for the demonstration. Changes to an approved scope or operation require new review. External deployment and GitHub publication follow their own owner authorization.
