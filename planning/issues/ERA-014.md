# ERA-014: Invalidate stale approval and revalidate before source effects

Epic: [EPIC-04](../epics/EPIC-04.md). Milestone: v0.1 end-to-end demonstration. Status: proposed.

Delivery and acceptance owner: project owner. Source-behavior decisions also require the accountable source owner.

## Outcome

An approved plan cannot execute after its scope, policy, selection, or authority becomes stale.

## Requirements and dependencies

Requirements: REQ-05, REQ-06, REQ-07.

Depends on: [ERA-013](ERA-013.md), [ERA-010](ERA-010.md).

## Intended implementation ownership

- `backend/proposals-decisions/`
- `backend/execution/`
- `adapters/`
- `contracts/`

## Acceptance criteria

- [ ] Bind approval to digest, source/tenant, action, selection, interval, mapping/policy versions, and expiry.
- [ ] Check current authorization and versions at dispatch; the adapter checks preconditions again before effects.
- [ ] A changed plan requires a new proposal and decision; preserve the earlier approval in history.
- [ ] Adapters unable to enforce atomic preconditions expose their limitation and use a reviewed safe checkpoint strategy.

## Verification

Change source data, mapping, policy, owner grants, proposal digest, and expiry between proposal/approval/dispatch; assert no unapproved expanded effects.

Retain commands/results and owner review against the exact candidate. Application checks are implemented with the issue; these are acceptance instructions, not claims that tests already exist.

## Boundaries

Use the [product requirements](../../docs/specification.md) and [architecture contract](../../docs/architecture.md). Operate on synthetic data for the demonstration. Changes to an approved scope or operation require new review. External deployment and GitHub publication follow their own owner authorization.
