# ERA-039: Implement the Redis cache adapter with safe expiry and recreation handling

Epic: [EPIC-10](../epics/EPIC-10.md). Milestone: v0.1 end-to-end demonstration. Status: proposed.

Delivery and acceptance owner: project owner. Source-behavior decisions also require the accountable source owner.

## Outcome

A source owner can approve cleanup of timestamped cache entries without deleting recreated or unrelated account data.

## Requirements and dependencies

Requirements: REQ-03, REQ-05, REQ-07, REQ-08, REQ-09, REQ-15.

Depends on: [ERA-038](ERA-038.md), [ERA-006](ERA-006.md), [ERA-017](ERA-017.md).

## Intended implementation ownership

- `adapters/cache/`
- `contracts/fixtures/cache/`
- `tests/cache-adapter/`

## Acceptance criteria

- [ ] Publish tenant/time-indexed cache inventory with timestamps, generations, TTL observations, explicit freshness/completeness, and whole-account exceptions.
- [ ] Freeze the approved key/generation selection and check it before invalidation; never use FLUSHDB, FLUSHALL, or unrestricted wildcard deletion.
- [ ] Persist operation identity and checkpoints outside disposable cache entries; duplicate delivery cannot delete a newer generation under an old plan.
- [ ] Distinguish removed, already absent/expired, changed generation, partial, and unknown results; preserve uncertainty about exact counts after interrupted receipt recording.
- [ ] Demonstrate that invalidation does not prevent later repopulation, and disclose that limit in proposal/receipt evidence.

## Verification

Contract-test the real Redis engine and durable adapter ledger; expire/recreate keys between approval and execution, drop receipts, restart, replay commands, and inspect only the selected synthetic tenant/generations.

Retain commands/results and owner review against the exact candidate. Application checks are implemented with the issue; these are acceptance instructions, not claims that tests already exist.
