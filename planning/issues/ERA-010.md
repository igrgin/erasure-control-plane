# ERA-010: Generate source-specific proposals with retention and selection preconditions

Epic: [EPIC-03](../epics/EPIC-03.md). Milestone: v0.1 end-to-end demonstration. Status: proposed.

Delivery and acceptance owner: project owner. Source-behavior decisions also require the accountable source owner.

## Outcome

A source owner sees what cleanup can actually affect and what the source must retain.

## Requirements and dependencies

Requirements: REQ-05, REQ-09.

Depends on: [ERA-009](ERA-009.md), [ERA-006](ERA-006.md).

## Intended implementation ownership

- `backend/proposals-decisions/`
- `adapters/transactional/`
- `contracts/`

## Acceptance criteria

- [ ] Separate requested scope, executable scope, retained categories, holds, expired/unobservable coverage, and unsupported selection precision.
- [ ] Bind plan to a frozen selection or reproducible source revision/precondition; disclose selection strategy.
- [ ] An unrepresentable interval blocks the source or produces explicit expanded scope requiring approval; no silent rounding.
- [ ] Display whole-account actions as such; distinguish proposed field transformation from certified anonymization.

## Verification

Use retention, hold, concurrent source-change, and coarse-time fixtures; prove changed selection cannot execute under the old approved plan.

Retain commands/results and owner review against the exact candidate. Application checks are implemented with the issue; these are acceptance instructions, not claims that tests already exist.

## Boundaries

Use the [product requirements](../../docs/specification.md) and [architecture contract](../../docs/architecture.md). Operate on synthetic data for the demonstration. Changes to an approved scope or operation require new review. External deployment and GitHub publication follow their own owner authorization.
